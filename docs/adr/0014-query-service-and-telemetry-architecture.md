# 0014 数据查询服务与态势感知看板架构

本项目在 35 大自动化日常与战斗流水线的基础上，针对玩家全景资产、伙伴阵型状态、小助手日常矩阵与背包消耗品盘点，确立无状态数据查询服务（Query Service）与 CLI 独立只读运行生命周期。

## Status

accepted

## Context

随着项目自动化日常的完善，用户对查看角色实时资产（铜钱、元宝、体力、声望等）、伙伴战力与品阶、小助手今日未完成日常矩阵，以及背包消耗道具余量的诉求日益迫切。然而：
1. **职责耦合风险**：若将查询直接挂载在 `TaskScheduler` 自动化流水线中，用户只想快速查看资产时必须等待或绕过庞大的日常任务，且流水线容易对游戏内状态产生副作用；
2. **协议与概念混淆**：前期探索中容易将玩家全局主体（Player: Mod 0）与参战伙伴实体（Role: Mod 5）混淆；
3. **安全红线防线**：小助手数据反序列化与背包消耗品（体力丹、经验丹、礼包盒）盘点必须维持纯只读态势感知，坚决杜绝因错误触发使用包而破坏零元宝与零资产误损底线。

## Considered Options

- **选项 1：无状态领域查询服务 + 独立 CLI 只读生命周期 (采纳)**：
  - **服务分层**：
    - `services/query_service.py`：`QueryService` 专职编排只读协议（Mod 0 Act 2、Mod 5 Act 2、Mod 2 Act 3、Mod 52 Act 0 等），返回强类型 DTO，并即查即存更新本地 `PlayerDatabase` (WAL)；
    - `services/query_formatter.py`：负责将 DTO 转换为高可读性控制台看板或标准 JSON；
  - **概念厘清**：明确划分 Player（玩家主体：Mod 0）与 Role（在阵主力伙伴：Mod 5 Act 2）；
  - **CLI 独立生命周期**：`main.py --query {assets,roles,assistant,pack,all}` 支持可选 `--json`，仅完成登录与数据检索，打印美化控制台看板或导出 JSON 后立即安全断连退出，不触发任何日常流水线；
  - **映射健壮性**：小助手配置 `AssistantItemManifest` 未知日常自动降级；背包采用 `ImportantItemRegistry` 核心战略消耗品清单 + `item_type` 宏观归类，坚决只读不自动消耗。
- **选项 2：将查询作为特殊 Task 纳入 TaskScheduler**：
  - 混淆了“状态变更任务”与“即时数据查询”的生命周期，增加了调度器的复杂性与响应延迟。
- **选项 3：激进基于小助手回包反向驱动流水线跳过/补做**：
  - 小助手回包存在服务端异步结算延迟，强依赖易导致偶发漏跑，增加系统脆弱性。

## Consequences

- **极速纯净查询**：CLI 查询毫秒级完成，杜绝不必要的发包与意外状态突变；
- **模型与协议解耦**：Player 与 Role 领域模型清晰，便于后续单独拓展阵型搭配与战力分析；
- **坚守安全红线**：所有查询动作均为 `[SAFE_READ]`，资产零消耗，不产生不可逆操作。
