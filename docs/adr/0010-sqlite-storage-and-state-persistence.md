# 0010 SQLite 协议字典与角色状态持久化存储架构

随着神仙道全量 880 模块协议元数据提取完毕（JSON 体积达 9.06 MB），且后续自动化日常运转、掉线重连恢复、战报掉落分析及离线决策需要频繁读写游戏资产与模块状态；直接依赖大体积 JSON 反复解析会导致显著的启动延迟与内存占用，而纯内存状态一旦进程退出便彻底丢失；为此，本项目决定引入基于标准库 `sqlite3` 的双库动静分离与异步 WAL 队列持久化架构，构建兼具强类型仓储与原生 SQL 检索能力的游戏数据存储系统。

## Status

accepted

## Considered Options

- **选项 1：动静分离双库 + 后台工作线程写入队列 (采纳)**：
  - **静态协议字典库 (`data/protocol_manifest.db`)**：首次冷启动时由 9.06 MB JSON 自动热转储入库（耗时 < 0.5s），全局只读共享，支持对模块、动作与常量的毫秒级 SQL 全文检索。
  - **角色私有存储库 (`data/storage_{server_id}_{player_id}.db`)**：按角色物理隔离，包含角色数值（`tb_player_profile`）、背包资产（`tb_inventory`）、子系统状态（`tb_module_state` 半结构化 JSON 载荷）、战报历史（`tb_battle_records` 自动滚动 1000 条）与风控流水（`tb_audit_log`）。
  - **异步队列写入与 WAL 并发**：主 `asyncio` 网络事件循环零阻塞，`EventBus` 监听到数据后投递至内存队列，后台专职单线程以 WAL 事务串行批量写入；所有外部查询均走无锁并发读取连接。
- **选项 2：单文件集中式 SQLite 数据库**：
  - 将所有区服、全量协议元数据与所有并发角色存入同一个 `.db` 文件。缺点是并发写时易触发数据库全局写锁竞争（Database Locked），且静态字典与用户数据混合不易清理维护。
- **选项 3：全工程引入 `aiosqlite` 异步 ORM**：
  - 依赖外部第三方库，破坏了工程规范中的“依赖克制”红线，且异步 ORM 并不能规避 SQLite 底层的物理写锁特性。
- **选项 4：文件系统单 JSON / YAML 平铺存储**：
  - 缺乏 ACID 事务支持，并发更新易损毁文件，且无法进行高效的 SQL 复杂条件过滤与统计。

## Consequences

- **极速冷启动**：协议元数据从 9MB JSON 解析的数百毫秒直接优化为 SQLite 毫秒级点查；
- **网络循环零阻塞**：所有数据库落盘走后台队列 + WAL 模式，确保网络套接字数据收发与心跳时序绝对不受 I/O 波动影响；
- **物理隔离与零污染**：多角色独立建库，数据清理和多开无锁竞争；
- **双模访问灵活**：上层业务既可通过 `GameStorage` 强类型仓储（Repository）享受自动补全，亦可调用 `query(sql)` 执行复杂数据挖掘与报表分析。
